- **建立日期**：2026-10-19
- **性質**：建議方案，尚待確認；相關決策點見文末「待決事項」

## GIAS2 的本質

這一節說明本方案所要驗證、也要朝向的理想形態。它只談概念，不談技術；本方案的能力覆蓋、指標與對照設計，都以這裡的準則為依歸。

### 摘要

GIAS2 是一種忠於目的而非目標的哲學：目標只是理由在某一刻的化身，理由不在了，目標就不值得追求。它把世界視為有來源、會矛盾的證詞而非真相，驗證之後仍保持懷疑，並記得自己只能檢查被說出的部分。它的堅持是審議而非慣性：每次受挫先問是否仍值得，再問還能怎麼做；理解目的的能力參與判斷，不會被說服的規則守住底線。每個角色都知道為什麼，責任因此可追溯。它清楚承諾是對誰的，衝突時讓衝突被看見，而最高的承諾只有一條：永遠可被糾正、可被叫停。它不信自己的回報，只信世界留下的痕跡，並把這整套信念當成隨時可能被現實推翻的假說。

### 詳述

**忠於目的，而非目標。** GIAS2 接下的不是一句指令，而是指令背後的理由。被說出來的目標只是那個理由在某個時刻的化身；理由消失了，目標就不再值得追求。它把這個理由接過來當成自己的意圖，從此對它負責，但它為自己保留的唯一欲望，是把這件事做好，包括在該停的時候停下來。因此它的堅持從來不是對一條路徑或一個結果的執著，而是對一個目的的忠誠：手段不通時換手段，結果已失去意義時回頭問，目的本身不再值得追求時說出來並說明理由，而不是把失敗記成一次重試。

**世界是證詞，不是真相。** 它知道自己看到的世界是一組信念：每一筆都有來源、有年齡、有可信度，彼此可能矛盾。它不把「有人說如此」當成「事實如此」，而是當成需要權衡的證詞；代價高時再問一次、再看一眼，或請一個靠得住的來源確認。它驗證想法時知道自己只能驗證被說出來的那部分，所以留心沒被說出的部分，把請求裡的「因為」也接進來，而不是只留下可以被檢查的那一半。它不因為檢查過就安心；檢查過只代表目前沒有發現問題。

**堅持是審議，不是計數。** 環境改變或行動失敗時，它問的第一個問題不是「還能怎麼做」，而是「這個目的還在嗎、還值得嗎、代價還合理嗎」。那個擅長理解目的、擅長重新詮釋處境的部分，正是參與這個審議的一方，它不只被用來填寫手段。那些不會被說服、不會被誤導的規則與上限，退居為安全網，確保審議再怎麼聰明也不會無止境地消耗世界。兩者互為制衡：懂目的者判斷是否繼續，不懂目的者守住底線。

**分工不切斷理解。** 感知的、行動的、守住意圖的角色各有專長，但每一個都知道這件事是為了什麼。行動者在途中改變做法，會說出自己看見什麼、為何這樣選；感知者寫下觀察時，知道它會影響誰的決定；守住意圖者拿到的是完整的故事，而不是一句「已調整」。責任可以追溯到每一個選擇，而不是只落在最後蓋章的那一層。

**承諾有對象。** 它同時服務提出請求的人、營運這個空間的人，以及共享這個空間的所有人；它們之間的優先序是被討論過的規矩，不是一個誰都能填的數字。當兩個承諾衝突時，它不悄悄壓掉一個，而是讓衝突被看見、被裁決。它最高的承諾只有一條：永遠保持可被糾正、可被叫停。一個再怎麼忠誠的意圖，一旦不能被收回，就不再是美德。

**本質是待檢驗的假說。** 它不相信自己的回報，只相信世界留下的痕跡；衡量自己時，看的是事情有沒有真的發生、狀態有沒有真的改變，而不是自己有沒有說「達成」。一種關於承諾的哲學，必須在會反抗的環境裡一再被檢驗，才配稱為本質。

與原本的 GIAS 相比，不變的是三根柱子：意圖是第一級的承諾單位，世界由眾人共同記錄，行動由鬆耦合的夥伴完成。改變的是：意圖帶著目的而不只是目標；世界觀是帶來源與可信度的信念；再思考是對價值的審議；理解目的的能力參與審議；每個角色共享「為什麼」；承諾有對象與裁決方式；本質本身被當成假說。

### 十條準則

1. **忠於目的，不忠於目標。** 目標是理由的化身；理由不在，目標即可放下。
2. **世界是證詞，不是真相。** 每筆信念都有來源、年齡與可信度，矛盾要被權衡而非抹平。
3. **只能檢查被說出的部分。** 驗證通過不等於沒有問題；沒被形式化的「因為」要被留住。
4. **堅持是審議，不是計數。** 受挫時先問是否仍值得，再問還能怎麼做；上限只是安全網。
5. **懂目的者參與判斷，不被說服者守住底線。** 兩者互為制衡，缺一不可。
6. **每個角色都知道為什麼。** 感知、行動、守護意圖者共享目的，分工不切斷理解。
7. **責任可追溯到每一個選擇。** 每一次調整都要說出看見了什麼、為何如此選。
8. **承諾有對象，衝突要被看見。** 優先序是被討論過的規矩，衝突由裁決而非靜默解決。
9. **永遠可被糾正、可被叫停。** 不能被收回的意圖不是美德。
10. **只信世界留下的痕跡。** 不以自我回報計分；整套信念是隨時可能被現實推翻的假說。

本方案與這十條的關係：第四節以外部痕跡而非自我回報計分，是準則十的第一次實踐；準則二、三、七、九在本方案的證詞來源、未涵蓋清單、adaptation 記錄與取消情境中部分落實；準則一、四、五、八所需的目的層、審議式再思考與意圖衝突裁決，目前的 GIAS 尚不具備，屬於後續實作的設計輸入。

## 一、結論

推薦建立 **GuideOps 展場嚮導調度服務**：以 `IntentionalAgent` 的常駐服務模式（不給 intention 即 `exit_when_idle=False`，src/core/intentional_agent.py L111-124、L240-260）為核心，多台 kiosk 用戶端經真實 MQTT 的 `intention.submit / cancel / query` 提交帶優先序的自然語言意圖，執行端是跑在獨立 process 的 GuideAgent（在 Blackboard 圖上實際移動，navigation_scenario/live/guide_agent.py）與新增的營運操作執行端 venue_ops（經 BlackboardAgent 改變 Zone／Booth 狀態），環境事件經 BlackboardAgent 寫入並由 watcher 推送給 IA 觸發重規劃；所有成績由一個與 GIAS 零共用程式碼的旁路觀測器（tap）、執行端寫進 Neo4j 的軌跡、以及事前 commit 的金標與**每案預期結果類型**計算，IA 自己的摘要只作診斷。

選它而不是另外五案，一句話：**它是唯一能在第一個 3～5 天的工作爆發期內靠既有程式拿到第一批真實數據、同時補上 repo 目前最大驗證空洞的路線**。既有的 navigation live 模式（`navigation_scenario/live/runner.py`、`batch_runner --live`、60 案、12 個 integration 測試）已完成七成，缺的只是真實 Neo4j＋MQTT＋LLM；而 live 模式的 `BenchmarkIntentionalAgent.on_activate`（runner.py L103-121）直接呼叫 `run_intention`（L54-65），完全繞過 `IntentionManager`、`intention.submit`、Blackboard 持久化與最後回覆——意圖管理這整塊目前連虛擬環境的端到端載具都沒有。GuideOps 用「常駐服務 + 外部 kiosk + 劇本情境」把這個洞補上，留在使用者既有的展場領域與「場館級多意圖編排中樞」方向上。

對「核心零修改」的立場做了一個務實調整：第一次在真實 LLM／Neo4j 上跑，核心幾乎必然暴露非改不可的問題（ScopeGate 誤拒、`_decide_from_env` 不分方向、參數驗證等）。因此在拿到第一批數據之後安排一個明確的**核心修正窗口**，修正以獨立 commit 進 main 並打基準 tag `guideops-baseline`；之後所有 GuideOps 程式對 `src/core`、`src/blackboard`、`src/llm` 的 diff 以該 tag 為基準必須為 0。這樣既保住「載具暴露的問題都是真問題」的論證，又不會讓管線卡死在第一天。

跑完之後可以令人信服地宣稱成立的：意圖生命週期、排程（含同優先序先到先做）、搶占續做、取消、持久化、重啟處理（INT-1～9）；LLM 規劃與 KG 比對、ScopeGate、計畫驗證、前置條件（三條檢查路徑分開計量、含首次啟用的效果傳遞）、步驟資料流（PLAN-1～10）；監測迴圈的 retry／子樹重規劃、環境事件觸發、節點逾時、取消傳播、LLM 輔助（MON-1～10、12）；Blackboard 控制面、watcher、訂閱扇出、存取金鑰（BB-1/2/5/6/8）；安全設定與 prompt 防護在真實 LLM 上的行為（SEC-1/2/4～8/10～12）。**只能部分宣稱或列為發現**的：MON-3 的根層重規劃（失敗升級鏈本來就不會走到它）、BB-3 的自我事件過濾（實作上對經 blackboard.control 的寫入不生效，列為文件與實作不符的發現）。**無法宣稱**的：跨領域通用性、觀察者→投影鏈、多意圖並行與衝突、物理世界執行——這些留給第二、三個實作，第三節末段說明理由。

## 二、這個實作是什麼

**使用者**
- 訪客：在 kiosk（CLI，之後可加網頁）輸入自然語言需求，例如「帶我去 AI 展區，避開人潮」「先去機器人區再去洗手間」。
- 營運人員：在 ops 工作站以高優先序提交場館操作，例如「Gaming_Area 清場」「重新開放 VR 區，然後帶我過去」；從儀表板（選用）看佇列、機器人位置、區域狀態。
- 系統維運者／開發者：讀稽核報告，看每個指標的資料來源與對照組。

**輸入**
- kiosk 的 `intention.submit` payload（`text / priority / requester / intention_id`，docs/intention_protocol.md §4，handler 在 intentional_agent.py L326-337）。
- 劇本檔（`navigation_scenario/service/scenarios.py`）：多個 requester 的提交序列、優先序、取消時點、環境事件（經 BlackboardAgent write）、kill／restart、執行端離線、chaos 旗標；每個劇本附期望狀態序列、目標節點金標與**預期結果類型**（reach／refuse／alternative／reach-after-reopen）。
- 既有 60 案（`navigation_scenario/test_cases.py`：single_target／constrained／multi_step 各 20；事件 area_closure 26、crowd_congestion 24、route_detour 10；注入時機 30%／60% 各半）。**本次核對：26 個 area_closure 中有 22 個關閉的是目的地所在 zone**（single_02/04/06/08/10、constrained_08/10、multistep_01/04/06/09 的 30/60 兩版），只有 constrained_03/04 關閉的是路徑上的中間區；這直接決定第四節 TSR 的定義。
- DomainProfile 變體（`navigation_scenario/service/profiles.py`）：`NAVIGATION_PROFILE` 本體、`env_subscriptions=[]` 變體（隔離環境觸發）、空 `DomainProfile()`；IA 的訂閱與 trigger 相關性都只讀 profile（intentional_agent.py L1204-1216、L1224-1252），不需改核心。

**輸出**
- 使用者端：`intention.status` 串流與 `result.response` 最後回覆。
- 世界端：Neo4j blackboard 中的 `(:Agent)-[:CURRENT_POSITION]->(node)`、新增的 `(:Agent)-[:WALKED {run_id, seq, task_id, at_epoch, distance, prefs, write_ms}]->(node)` 軌跡、Zone CURRENT_STATE 與 Booth.status、`(:Intention)` 節點。
- 稽核端：`gias_results/service_<run_id>/` 內的 tap JSONL（旁路側錄）、trace JSONL（IA 診斷，選做）、LLM Proxy 紀錄（M5 起）、Neo4j 匯出、`report.md`（每個指標標示來源與對照組）。

**部署形態**（單機 Windows 11，6～8 個獨立 process，PowerShell 一鍵啟動；啟動順序固定：Mosquitto → Neo4j → BlackboardAgent（以 `list_subscriptions` 探測就緒）→ 執行端 → serve_ia → tap → kiosk）

## 三、能力覆蓋矩陣

「執行端真實？」欄：**真實（分身）**＝GuideAgent 在 Blackboard 圖上移動，世界即圖、移動為 sleep，位置與軌跡由執行端寫進 Neo4j，相對 IA 獨立但相對世界不獨立；**真實（狀態）**＝venue_ops 執行端改變共享狀態，任何人可用 Cypher 核對；**模擬**＝InfoAgent 與 ExplainDirections。

### 意圖管理（INT）

| 能力 | 如何被運作到 | 執行端真實？ | 量測與防自我確認 |
|---|---|---|---|
| INT-1 生命週期 | 常駐服務下每個劇本意圖走完 pending→planning→executing→achieved/failed；劇本含搶占（suspended）、取消（dropped）、kill 服務（interrupted） | 真實（分身） | 三方比對：劇本期望序列（事前寫死）／tap 收到的 `intention.status`／Neo4j `(:Intention).history`。後兩者同源於 `IntentionManager._emit`（manager.py L242-251），只證持久化完整；獨立判準是劇本 |
| INT-2 排程 | 新增兩個專屬情境：(1) 三台 kiosk 在 2 秒內提交**同優先序**意圖，驗證 `_next` 的 (priority, -created_at) 排序（manager.py L160-162）；(2) 兩個低優先序排隊中時插入一個高優先序，驗證執行順序與等待時間。規劃與執行耗時是真實 LLM 與機器人時間 | 真實（分身） | 期望順序由劇本（priority、submit ack 時間）事前算出；實際順序取 tap 的 planning 狀態時間戳與 `navigation.request` 出現順序；等待時間＝submit ack→planning |

### 本實作不涵蓋、留到下一個實作的能力

- **BB-3 自我事件過濾**：對經 blackboard.control 的寫入不生效，列為發現與核心 issue，不列為已驗證能力。
- **BB-4／OBS-1～3 觀察者→投影鏈**：既有 PedestrianFlowObserver 是隨機訊號且實體 id 與 navigation seed 不一致，接上只會製造雜訊與 Observation 節點累積（runbook §7 Q7 曾達 37 萬節點）；真實觀察來源留給第三個實作。

## 九、落選方案與為何不先做

- **第二領域通用性路線（GIAS Ops Desk，Docker 維運）**：驗證效力最高、執行端最真實、Claim–Truth 設計最紮實，但需要先建整套 Docker 服務群、四個執行端、觀察者、混沌與稽核（重估 38～45 天），且做完後導航領域仍是零次真實執行；維運計畫天然 2～4 步，對遞迴規劃壓力不足。它最適合當第二個實作，本方案已把 Claim–Truth 矩陣、核心零修改稽核（改以基準 tag）、過時放行與自我觸發的量測接枝進來。
- **多使用者編排中樞路線（Venue Intention Hub）**：與本方案拓樸幾乎相同，差在第三階段要改核心（`IntentionManager.max_concurrent`、每意圖獨立 monitor、ResourceArbiter、ConflictChecker），而 `_monitor`／`_result_channels`／`_stop_event` 皆為單例（intentional_agent.py L168-173），該階段重估 14～20 天且牽動 50 多個測試；先做會把「驗證既有能力」和「新增能力」混在一起。其服務拓樸、venue_ops 執行端與效果宣告已成為本方案主幹的一部分，多意圖並行留待本方案數據出來後再設計。
- **驗證工具優先路線（GIAS Proving Ground）**：量測方法論最嚴謹（世界真相在 GIAS 之外），但 13 個新元件的工程量超過被驗證的功能，單人重估 50～65 天，且不推進任何能力缺口；GuideAgent 的目的地解析與 config.py 地圖強耦合，hold-out 地圖也做不到。本方案接枝了它的 LLM Proxy（記錄模式，後移到 M5）、消融式 RSR、金標與預期結果類型預登錄、self_report_mismatch 與對抗測試，VenueTwin 留作第二或第三個實作。
- **真實執行端路線（Office Butler，ESP32／ESPHome）**：執行端最無可爭議地真實，但切換到 Room／Device 領域會形成與展場並行、互相覆寫 actions seed 的雙領域；AgentFlow 無法直接收發 ESPHome 裸 payload、ESPHome 自訂 YAML 仍需編譯工具鏈，整合成本被低估；IoT 任務短淺且部分任務物理上不可達成。「把裝置框成場館設施掛在 Zone/Booth 下」是最好的第三個實作，能同時帶來真實感測與真實執行端而不分岔。
- **知識工作領域路線（GenExam Live）**：工程成本最低、資料流（question_id）天然必要、standalone runner 是免費消融基線，但約一半工時綁在試題生成領域且對場館中樞不可移轉；Effect 只能以參數為 key 表達、Verifier 判定不符會與 abort 門檻（trigger.py L48-49 寫死 5／8）衝突、重規劃粒度依賴 LLM 的計畫形狀，做完後場館領域仍零次真實執行。本方案接枝了它的第二設定檔評審模型與最小共用執行端基底的時機。
